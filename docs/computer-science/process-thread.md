# 프로세스와 스레드

프로그램은 실행할 코드와 데이터이고 프로세스는 실행 중인 프로그램의 주소 공간·자원·실행 상태를 관리하는 단위다. 스레드는 프로세스 안에서 실행을 이어가는 흐름이다.

## 무엇을 공유하는가

| 항목 | 별도 프로세스 | 같은 프로세스의 스레드 |
| --- | --- | --- |
| 가상 주소 공간 | 기본적으로 분리, 명시적 공유 메모리 가능 | 공유 |
| 코드·전역 데이터·힙 객체 | 기본적으로 서로 직접 접근하지 못함 | 같은 주소 공간에서 접근 가능 |
| 스택·레지스터·실행 위치 | 실행 흐름마다 관리 | 스레드마다 관리 |
| 통신 | 파이프·소켓·공유 메모리 등의 IPC | 공유 데이터와 동기화 도구 |
| 장애 영향 | 분리된 프로세스로 영향 범위를 줄일 수 있음 | 메모리 손상 등이 프로세스 전체에 영향을 줄 수 있음 |

스택이 스레드마다 있다는 사실과 스택 주소에 다른 스레드가 절대 접근할 수 없다는 주장은 다르다. 지역 변수가 가리키는 힙 객체는 다른 스레드도 참조할 수 있다. 공유 여부는 변수 이름이나 저장 위치보다 실제 참조와 접근 방식으로 판단한다.

## 상태와 컨텍스트 전환

일반적인 상태 흐름은 준비 → 실행 → 대기 → 준비다. CPU를 배정받아 실행하다가 I/O나 락을 기다리면 대기하고, 조건이 충족되면 다시 실행 후보가 된다. OS별 실제 상태 이름과 세부 전이는 다를 수 있다.

컨텍스트 전환은 현재 흐름의 실행 위치·레지스터 등을 저장하고 다른 흐름의 상태를 복구하는 과정이다. 프로세스가 바뀌면 주소 공간 전환도 관여할 수 있다. 같은 프로세스의 스레드 전환은 주소 공간을 유지할 수 있지만 스케줄링·캐시 비용은 남는다. PCB·스레드 관리 구조에 ID, 상태와 자원 관련 정보를 기록하며 실제 구조는 OS 구현에 따른다.

CPU 시간은 실행에 사용한 CPU 시간을, wall-clock 시간은 대기까지 포함한 실제 경과 시간을 뜻한다. 작업이 I/O를 기다리면 두 값이 달라진다. 스레드 수의 효과는 CPU 코어, 대기 비율, 락 경합·메모리·downstream 한계로 판단한다.

## 통신과 공유의 예

작업 프로세스 둘이 소켓으로 메시지를 주고받으면 직렬화·전송·응답 처리 규칙이 필요하다. 공유 메모리는 복사 비용을 줄일 수 있지만 접근 순서를 제어해야 한다. IPC가 무조건 느리거나 스레드가 항상 더 빠르다는 보장은 없다.

같은 프로세스의 요청 스레드가 캐시를 공유하면 조회는 간단하지만 읽기·계산·쓰기의 복합 작업에는 경쟁 상태가 생길 수 있다. [동기화와 교착 상태](../operating-systems/synchronization.md)의 실행 순서와 락 예제로 이어진다.

## thread safety와 전용 저장소

thread-safe한 코드는 계약상 허용된 동시 호출에서도 데이터 규칙과 결과를 유지한다. 불변 데이터, 소유권 분리, 락과 적절한 원자 연산을 선택한다. 원자 변수 하나를 사용했다고 여러 변수의 결합 규칙까지 자동 보호되는 것은 아니다.

Java ThreadLocal은 각 스레드가 독립된 값을 가질 수 있게 한다. 초기화 과정에서 같은 공유 객체를 넣었다면 그 객체는 여전히 공유될 수 있다. 스레드 풀에서 요청 데이터를 보관할 때는 작업 종료 시 `remove()` 등으로 수명과 정리를 관리한다. 스레드 풀은 실행 스레드를 재사용하는 수단이며 모든 workload의 최적 스레드 수가 같지는 않다.
