# CS 면접 답변과 꼬리 질문 26개

각 답변은 말로 설명할 출발점이다. 짧은 답변을 먼저 말하고 예시와 적용 조건을 붙인다. 개인 경험이 없으면 아래 학습 예시를 실제 운영 경험처럼 말하지 않는다. [질문 목록과 학습 순서](cs-interview.md)에서 분야별로 찾아볼 수 있다.

## Q01

**프로세스와 스레드는 어떻게 다른가?**

**짧은 답변:** 프로세스는 실행 중인 프로그램의 주소 공간과 자원을 관리하는 단위이고, 스레드는 그 안의 실행 흐름이다. 같은 프로세스의 스레드는 주소 공간을 공유하면서 각자의 스택·레지스터 상태를 가진다. 공유가 쉬운 만큼 동기화와 장애 전파를 고려해야 한다.

**예시:** 서버의 여러 스레드가 같은 캐시를 쓰면 복사 없이 접근할 수 있지만 동시에 갱신하는 규칙이 필요하다. 별도 프로세스라면 소켓·파이프·공유 메모리 같은 IPC를 선택한다.

**꼬리 질문:** 컨텍스트 전환에서 저장하는 정보는 무엇인가? 지역 변수로 받은 객체는 무조건 스레드 전용인가?

[원리와 비교표](../computer-science/process-thread.md)

## Q02

**동시성과 병렬성은 어떻게 다른가?**

**짧은 답변:** 동시성은 여러 작업의 진행이 겹치게 구성하는 것이고, 병렬성은 여러 작업을 실제로 동시에 실행하는 것이다. 한 코어도 작업을 번갈아 실행하며 동시성을 제공할 수 있다. 여러 코어가 있다고 모든 프로그램이 자동으로 병렬화되지는 않는다.

**예시:** 응답을 기다리는 동안 다른 HTTP 요청을 진행하면 I/O 대기가 겹친다. 큰 계산을 여러 코어에 분배하는 것은 별도의 병렬 실행 설계다.

**꼬리 질문:** CPU 작업과 I/O 작업에서 스레드 수를 늘리는 효과가 왜 다른가?

[로컬 I/O 실험](../computer-science/async-io-case-study.md)

## Q03

**비동기와 논블로킹은 같은 말인가?**

**짧은 답변:** 논블로킹은 호출이 완료를 기다리며 스레드를 붙잡지 않고 반환하는 성질이다. 비동기는 완료 결과를 이후의 통지·callback·future 등으로 받는 실행 계약이다. 어떤 작업을 어떤 관점에서 분류하는지 먼저 정해야 한다.

**예시:** nonblocking read가 아직 읽을 데이터가 없다고 반환하면 호출자가 readiness를 기다린 뒤 다시 시도할 수 있다. 비동기 읽기는 작업을 제출하고 완료 결과를 나중에 받는다.

**꼬리 질문:** await가 호출 스레드를 항상 바꾸는가? 이벤트 루프에서 blocking 함수를 호출하면?

[콜백과 코루틴](../computer-science/callback-and-coroutine.md)

## Q04

**포인터와 메모리 주소를 어떻게 설명할 것인가?**

**짧은 답변:** 포인터는 특정 타입의 객체나 함수 등을 가리키는 값이다. C에서 포인터를 역참조하려면 가리키는 객체의 수명과 접근 범위가 유효해야 한다. 포인터 연산은 단순히 정수 주소에 1바이트를 더하는 것과 다르다.

**예시:** 정수 배열 arr에서 `arr + 1`은 다음 정수 원소를 가리키고 `*(arr + 1)`은 그 값을 읽는다. 해제한 메모리의 포인터가 남아 있어도 객체는 더 이상 유효하지 않다.

**꼬리 질문:** 배열과 포인터는 같은 타입인가? 지역 변수의 주소를 반환하면 어떤 문제가 있는가?

[C 예제](../computer-science/memory-and-pointers.md)

## Q05

**컴파일과 링킹은 각각 무엇을 하는가?**

**짧은 답변:** 컴파일은 소스를 분석해 목적 코드 등으로 변환하고, 링킹은 여러 목적 파일과 라이브러리의 심볼을 연결하고 실행에 필요한 형태를 만든다. 실제 언어·도구 체인의 단계는 다를 수 있다.

**예시:** 함수 선언을 알아 컴파일은 성공했지만 함수 정의가 링크 대상에 없으면 undefined reference 같은 오류가 날 수 있다. 동적 라이브러리는 실행 시 로더가 관여한다.

**꼬리 질문:** 정적·동적 링킹의 배포 비용과 실행 환경 의존성은 어떻게 다른가?

[컴파일과 링킹](../computer-science/compilation.md)

## Q06

**코루틴은 스레드와 어떤 관계가 있는가?**

**짧은 답변:** 코루틴은 상태를 유지하며 중단·재개할 수 있는 실행 단위다. 스레드에 어떻게 배치되는지는 언어와 runtime에 달린다. Python asyncio의 Task는 이벤트 루프에서 협력적으로 실행하며 await 자체가 CPU 병렬 실행을 보장하지 않는다.

**예시:** 여러 코루틴이 네트워크 결과를 기다리는 동안 실행을 양보한다. 한 코루틴이 긴 동기 계산을 계속하면 같은 이벤트 루프의 다른 작업도 지연된다.

**꼬리 질문:** blocking I/O를 분리하려면? 취소와 timeout을 어떻게 전파할 것인가?

[코루틴과 Task](../computer-science/callback-and-coroutine.md)

## Q07

**웹 주소를 입력하면 어떤 일이 일어나는가?**

**짧은 답변:** 일반적인 새 HTTPS 요청은 이름 해석, 연결, TLS 인증·키 협상, HTTP 요청·응답, 브라우저의 해석과 렌더링으로 이어진다. DNS·응답 캐시와 연결 재사용은 일부 단계를 줄인다. HTTP/3는 QUIC를 사용하므로 모든 HTTP를 TCP의 과정으로 설명하지 않는다.

**예시:** 첫 문서 응답 이후 CSS·스크립트·이미지 요청이 이어질 수 있다. 서버 응답 시간만 빨라도 렌더링이나 추가 자원 때문에 전체 표시가 느릴 수 있다.

**꼬리 질문:** DNS 조회와 TLS는 무엇을 각각 확인하는가? 재사용 연결에서는 무엇이 달라지는가?

[네트워크 흐름](../networking/network.md) · [관찰 실습](../networking/dns-process.md)

## Q08

**TCP와 UDP는 어떤 기준으로 선택하는가?**

**짧은 답변:** TCP는 순서 있는 바이트 스트림과 재전송·흐름·혼잡 제어를 제공한다. UDP는 데이터그램을 제공하며 같은 보장을 기본 제공하지 않는다. 순서·손실·지연 요구와 상위 프로토콜을 보고 선택한다.

**예시:** 파일을 온전히 전달하는 것과 늦은 음성 패킷의 효용은 다르다. UDP 위의 QUIC처럼 상위 계층에서 신뢰성과 혼잡 제어를 제공할 수도 있다.

**꼬리 질문:** 흐름 제어와 혼잡 제어는 누구의 과부하를 줄이는가? TCP의 read 한 번이 send 한 번과 대응하는가?

[TCP와 UDP](../networking/network.md)

## Q09

**리버스 프록시를 왜 사용하는가?**

**짧은 답변:** 서버 앞에서 요청을 받아 뒤의 서버에 전달하며 라우팅, 부하 분산, TLS 종료 같은 기능을 맡길 수 있다. 진입 정책을 모을 수 있지만 프록시 자체의 장애·용량·timeout도 설계해야 한다.

**예시:** `/api`와 정적 파일을 다른 대상으로 보내고 backend의 health check 결과에 따라 요청을 분배한다. TLS를 종료했다면 backend 구간의 암호화 요구도 따로 정한다.

**꼬리 질문:** L4와 L7 부하 분산의 기준은? 원래 사용자 IP와 신뢰할 헤더는 어떻게 관리하는가?

[리버스 프록시](../networking/reverse-proxy.md)

## Q10

**CORS는 어떤 문제를 다루는가?**

**짧은 답변:** CORS는 다른 origin의 응답을 브라우저 스크립트가 읽도록 서버가 허용하는 프로토콜이다. Origin은 scheme·host·port로 구분한다. 서버 인증이나 CSRF 방어를 대신하지 않는다.

**예시:** 프런트엔드와 API의 origin이 다르면 응답 접근 허용이 필요할 수 있다. CORS 오류라도 단순 요청은 서버에 이미 도착했을 수 있다.

**꼬리 질문:** preflight는 언제 필요한가? 쿠키를 포함한 요청에 허용 origin을 `*`로 둘 수 있는가?

[CORS와 CSRF](../security/cors/cors.md)

## Q11

**SQL과 NoSQL은 어떻게 선택하는가?**

**짧은 답변:** 데이터 모델, 필요한 질의·제약·트랜잭션, 확장과 운영 요구를 비교한다. SQL은 질의 언어이고 NoSQL은 여러 저장 모델의 묶음이므로 SQL 여부만으로 성능이나 일관성을 단정하지 않는다.

**예시:** 여러 관계를 조인하고 제약을 유지하는 업무와 키 하나로 문서를 가져오는 업무는 다른 접근 패턴이다. 제품의 기능과 대표 데이터로 판단한다.

**꼬리 질문:** 문서 DB에도 트랜잭션이 있는가? 정규화와 비정규화의 갱신 비용은?

[SQL 비교](../databases/sql.md) · [NoSQL](../databases/nosql.md)

## Q12

**인덱스는 언제 이득이고 언제 비용이 되는가?**

**짧은 답변:** 인덱스는 조건에 맞는 후보나 정렬된 순서에 접근하도록 돕지만 공간과 갱신 비용을 추가한다. 선택도·통계·테이블 크기·질의에 따라 전체 스캔이 더 나을 수도 있다.

**예시:** 고객별 최근 주문에는 `(customer_id, created_at)`을 후보로 검토한다. 대표 데이터를 넣고 인덱스 전후 scan·sort·행 수·buffer를 비교해야 한다.

**꼬리 질문:** 복합 인덱스의 열 순서가 왜 중요한가? EXPLAIN과 EXPLAIN ANALYZE는 무엇이 다른가?

[재현 가능한 인덱스 실습](../databases/index-tuning.md)

## Q13

**CAP 정리는 어떤 상황의 선택을 설명하는가?**

**짧은 답변:** 네트워크 분할 중 모든 정상 노드의 연산을 완료시키는 가용성과 선형화 가능한 일관성을 함께 보장할 수 없다는 제약이다. 평상시에 세 가지 중 아무 두 개를 고른다는 설명은 부족하다.

**예시:** 두 지역의 재고 복제본이 통신하지 못할 때 양쪽 판매를 계속 허용하면 상태가 달라질 수 있다. 강한 일관성을 유지하려면 일부 요청의 완료를 제한해야 한다.

**꼬리 질문:** CAP의 가용성과 운영 SLO는 같은가? PACELC는 정상 상태에서 무엇을 비교하는가?

[CAP와 PACELC](../databases/cap-theorem.md)

## Q14

**캐시를 도입하면 어떤 문제가 추가되는가?**

**짧은 답변:** 원본 접근과 지연을 줄일 수 있지만 오래된 값, 무효화, 만료 동시 발생과 장애 시 원본 부하를 관리해야 한다. 키와 일관성 요구를 먼저 정한다.

**예시:** 인기 글 캐시가 한꺼번에 만료되면 요청이 모두 DB로 갈 수 있다. TTL 분산이나 동일 값의 재생성 동시성 제한을 고려한다.

**꼬리 질문:** DB 변경과 캐시 삭제 사이에 장애가 나면? 개인화 응답을 공유 캐시해도 되는가?

[Redis 활용](../databases/redis/redis-usecase.md) · [게시판 설계](../architecture/web-service-design.md)

## Q15

**세션과 JWT 기반 인증은 무엇이 다른가?**

**짧은 답변:** 서버 세션은 ID로 서버 측 인증 상태를 조회하고 서명된 JWT는 토큰의 서명과 claim을 검증한다. JWT 서명은 내용을 숨기지 않으며 즉시 철회·권한 변경 요구에는 상태나 별도 정책이 필요할 수 있다.

**예시:** 로그아웃한 토큰을 즉시 막으려면 단순히 브라우저에서 지우는 것만으로는 부족할 수 있다. 서버 상태 조회, 만료와 철회 전략을 비교한다.

**꼬리 질문:** 쿠키는 세션만 담는가? JWT를 쿠키에 저장하면 CSRF 문제가 사라지는가?

[세션과 토큰](../security/session-token/session-token.md)

## Q16

**TLS 인증서는 어떤 역할을 하는가?**

**짧은 답변:** 공개키와 주체 정보를 연결하고 신뢰 체인·유효성·호스트 이름 등을 확인해 상대 인증에 사용한다. 인증서가 있다고 사이트의 업무 내용까지 안전하거나 정직하다는 보장은 없다.

**예시:** 요청한 hostname과 인증서의 대상 이름이 맞지 않으면 연결 상대를 검증할 수 없다. TLS 1.3의 키 협상과 인증서의 서명 키 역할도 구분한다.

**꼬리 질문:** 인증서 RSA 키가 있으면 RSA key exchange를 하는가? 인증서 체인은 왜 필요한가?

[X.509와 TLS](../security/x509-certificates.md)

## Q17

**컨테이너와 가상머신은 어떻게 다른가?**

**짧은 답변:** 일반적인 Linux 컨테이너는 호스트 커널을 공유하며 namespace·cgroup 등으로 격리·자원 관리를 한다. VM은 가상 하드웨어 위에 별도의 게스트 커널을 실행한다. 격리 요구, 호환성과 자원 비용을 함께 비교한다.

**예시:** 하나의 Linux 환경에서 앱을 분리하는 것과 서로 다른 게스트 OS를 실행하는 것은 다른 요구다. Docker Desktop은 VM 안에서 Linux 컨테이너를 실행할 수 있다.

**꼬리 질문:** KVM과 QEMU의 역할은? 컨테이너의 root 권한을 왜 주의해야 하는가?

[가상화 비교](../computer-science/virtualization.md) · [Docker](../containers/docker/docker.md)

## Q18

**CDN은 언제 효과적이고 무엇을 주의해야 하는가?**

**짧은 답변:** 사용자 가까운 곳에서 캐시 가능한 콘텐츠를 제공해 지연과 원본 부하를 줄일 수 있다. 캐시 키·TTL·무효화·인증 경계를 잘못 정하면 오래되거나 다른 사용자의 응답이 전달될 수 있다.

**예시:** 버전이 붙은 정적 파일은 오래 캐시하고 로그인 사용자별 응답은 별도 정책으로 다룬다. 원본 수정이 모든 edge에 즉시 반영된다고 가정하지 않는다.

**꼬리 질문:** query·cookie가 cache key에 포함되면 적중률은? no-cache와 no-store의 차이는?

[CDN](../cloud/aws/cloudfront.md) · [HTTP 캐시](../networking/http-semantics.md)

## Q19

**서비스가 느려졌다면 어디부터 확인하는가?**

**짧은 답변:** 영향을 받는 기능·시간·범위를 정하고 최근 변경과 지연·오류·트래픽·자원 지표를 확인한다. 클라이언트, 네트워크, 애플리케이션, DB와 외부 호출의 시간을 나누어 가설을 검증한다.

**예시:** 평균 응답은 같은데 p99만 늘면 특정 요청, lock 대기, cache miss나 외부 timeout을 살펴볼 수 있다. 상관관계를 곧바로 원인으로 확정하지 않는다.

**꼬리 질문:** CPU가 낮아도 서버가 느릴 수 있는가? 관찰한 병목을 어떻게 재현하고 개선 결과를 비교하는가?

[성능 진단](../devops/troubleshooting.md) · [로그 분석](../devops/monitoring/log.md)

## Q20

**서비스의 신뢰성을 어떤 지표로 설명하는가?**

**짧은 답변:** 사용자 관점의 성공 비율·지연 같은 SLI를 정하고 기간과 목표값으로 SLO를 정의한다. 허용한 실패량인 오류 예산과 소모 속도로 안정화·배포 판단을 연결한다.

**예시:** 30일의 적격 요청 100만 건 중 99.9% 성공을 목표로 한다면 허용 실패 요청은 1,000건이다. 시간 기반 가용성 목표와 요청 기반 목표는 구분한다.

**꼬리 질문:** 어떤 요청을 분모에서 제외하는가? 짧은 장애가 예산을 빠르게 소모하면 경보는?

[SRE와 오류 예산](../devops/sre/sre.md)

## Q21

**배열과 연결 리스트를 어떻게 선택하는가?**

**짧은 답변:** 배열은 인덱스 접근과 연속 순회에 적합하고 중간 삽입·삭제에 이동 비용이 든다. 연결 리스트는 필요한 노드·링크를 알고 있으면 삽입·삭제가 간단하지만 위치 탐색과 노드 할당 비용을 고려해야 한다.

**예시:** 인덱스로 자주 읽는 데이터와 양 끝만 사용하는 큐의 요구는 다르다. Python list는 동적 배열이고 큐에는 deque를 검토한다.

**꼬리 질문:** 평균·최악·분할 상환 O(1)은 어떻게 다른가? 해시 충돌은 어떻게 처리하는가?

[자료구조와 복잡도](../computer-science/data-structures.md)

## Q22

**BFS와 DFS는 어떻게 다른가?**

**짧은 답변:** BFS는 큐로 가까운 정점부터, DFS는 스택이나 재귀로 한 경로부터 탐색한다. 인접 리스트 전체 탐색은 O(V + E)지만 BFS의 최단 거리 보장은 간선 비용이 같은 조건에서 설명한다.

**예시:** 모든 이동 비용이 1인 미로의 최단 이동 수는 BFS로 구할 수 있다. 가중치가 다르면 다른 알고리즘이 필요하다.

**꼬리 질문:** 방문 표시는 언제 하는가? 순환이나 연결되지 않은 정점은 어떻게 처리하는가?

[실행 가능한 BFS와 이진 탐색](../computer-science/algorithms.md)

## Q23

**트랜잭션 격리 수준과 MVCC는 무엇인가?**

**짧은 답변:** 격리 수준은 동시 트랜잭션이 어떤 변경을 볼 수 있고 어떤 이상 현상을 허용하는지 정한다. MVCC는 여러 버전과 스냅샷으로 관찰할 값을 정하는 구현 방법이며 모든 충돌을 없애지는 않는다.

**예시:** PostgreSQL Read Committed에서는 같은 트랜잭션의 두 SELECT 사이에 다른 commit이 보일 수 있다. Repeatable Read는 유지된 스냅샷으로 조회하지만 모든 실행이 직렬화되는 것은 아니다.

**꼬리 질문:** 초과 판매를 어떻게 막는가? Serializable의 재시도는 어디까지 다시 실행하는가?

[두 세션 실습과 재고 갱신](../databases/transactions.md)

## Q24

**교착 상태는 왜 생기며 어떻게 대응하는가?**

**짧은 답변:** 서로가 가진 자원을 기다리는 순환 대기로 진행하지 못하는 상태다. 상호 배제·보유하며 대기·비선점·순환 대기 조건을 보고 락 획득 순서, 자원 확보 방식이나 감지 후 복구를 설계한다.

**예시:** A가 X를 잡고 Y를 기다리고 B가 Y를 잡고 X를 기다린다. 모두 X → Y 순서로 획득하게 하면 이 순환을 예방할 수 있다.

**꼬리 질문:** timeout만 넣으면 충분한가? 기아와 livelock은 무엇이 다른가?

[동기화와 교착](../operating-systems/synchronization.md)

## Q25

**TLB miss와 페이지 폴트는 무엇이 다른가?**

**짧은 답변:** TLB miss는 변환 캐시에 정보가 없어 페이지 테이블에서 매핑을 구해야 하는 경우다. 페이지 폴트는 페이지 상태나 권한 때문에 OS 처리가 필요한 예외다. miss가 모두 fault가 아니고 fault가 모두 디스크 읽기도 아니다.

**예시:** 유효한 페이지 매핑은 TLB miss 뒤 곧바로 얻을 수 있다. 처음 접근한 페이지의 할당이나 copy-on-write도 fault 처리 이유가 될 수 있다.

**꼬리 질문:** 두 프로세스가 같은 가상 주소를 사용하면? RSS와 가상 주소 공간 크기는 같은가?

[가상 메모리](../operating-systems/virtual-memory.md)

## Q26

**timeout 이후 주문을 재시도해도 되는가?**

**짧은 답변:** 응답을 못 받았어도 서버가 이미 처리했을 수 있다. 같은 논리적 요청을 식별하는 키, 요청 내용 검사와 결과 확인을 갖추고 제한된 재시도를 설계한다. HTTP 메서드 이름만으로 업무 중복까지 해결되지는 않는다.

**예시:** 같은 사용자·주문 키는 DB에서 유일하게 관리하고 결과 미확정 결제는 공급자 결과를 확인한다. outbox의 중복 전송에도 소비자가 같은 이벤트를 안전하게 처리해야 한다.

**꼬리 질문:** 같은 키로 다른 요청이 오면? DB 트랜잭션에 외부 결제를 넣으면 함께 rollback되는가?

[HTTP 의미와 재시도](../networking/http-semantics.md) · [주문 설계](../architecture/web-service-design.md)
