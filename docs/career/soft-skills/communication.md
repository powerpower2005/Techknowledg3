# 기술 커뮤니케이션

## 사실과 요청을 구분하기

공유 내용에는 관찰한 사실, 해석, 제안, 상대에게 필요한 결정을 나누어 적는다. “서버가 느리다”보다 “14시 이후 검색 p95가 늘었고 DB 대기 시간이 같이 증가했다. 쿼리 계획을 확인하겠다”가 다음 행동을 정하기 쉽다. 예시 수치는 실제 장애 기록을 뜻하지 않는다.

## 장애 공유 템플릿

영향: 어떤 사용자 기능이 언제부터 영향을 받는가. 근거: 확인한 지표와 요청 ID는 무엇인가. 조치: 현재 완화와 결과는 무엇인가. 다음: 담당자와 다음 확인 시각은 언제인가. 확인되지 않은 원인은 가설로 표시한다.

## 리뷰와 회의

리뷰는 사람보다 변경의 동작과 근거를 다룬다. 필수 수정과 선택적인 제안을 구분한다. 회의 전에 결정할 질문을 보내고 이후에는 결정·근거·담당자·미결정만 간결하게 남긴다. 전달한 내용이 이해됐는지 작업 기준이나 재현 절차로 확인한다.

## 적용 범위와 확인

일반적인 기술 협업과 의사소통 기준으로 설명했습니다. 기술 내용의 문서 검토일은 2026-10-06입니다. 예제를 실제 제품 환경에서 실행했다는 뜻은 아닙니다.
